# Алгоритм планирования

Численные сравнения с прежними версиями в этом документе — исторические результаты авторов. Актуальные воспроизводимые измерения и ограничения: [аудит 25.09.2026](AUDIT_2026-09-25.md).

## Постановка

Дано:
- область съемки R (MultiPolygon, возможны отверстия);
- запретные зоны Z_i: 2D, 3D (диапазон высот) или 4D (с окном действия);
- высотные препятствия O_j с высотой h_j;
- разрешенное воздушное пространство A;
- площадки S (основные и резервные);
- парк БВС: типы m, количество n_m, ТТХ, полезная нагрузка;
- требуемый GSD, перекрытия, ветер (w, направление), дата начала.

Найти:
- множество вылетов k, у каждого борт d(k), площадка s(k) и 4D-траектория x_k(t);
- покрытие P = ⋃ полос_k ⊇ R \ (Z ∪ O ∪ ¬A);
- время работ T = max_k t_посадки(k) + 600 с − t_0, включая подготовку, замену АКБ, возврат всех бортов и итоговую выгрузку;
- суммарный налет F = Σ_k (t_посадки − t_взлета).

Критерии: `min T` (режим *time*), `min F + λ·N_взлетов` (режим *flight*) или компромисс по Чебышёву (режим *balanced*):

`min J = max(0.5·t, 0.5·f) + 0.01·(t + f)`,
где `t = (T − Tmin)/(Tmax − Tmin)`, `f = (F − Fmin)/(Fmax − Fmin)` по диапазонам кандидатов первичной сетки. Границы фиксированы для последующего поиска и финального отбора. В реализации `J` умножается на `Tmin` для согласования масштаба со штрафами; износ и превышение срока добавляются отдельно. Заданный срок `T ≤ T_срок` проверяется независимо для всех режимов. Обработка нулевых диапазонов и состав штрафов описаны в [ТЗ режима «Баланс»](FINAL_SPRINT.md#критерий).

Жесткие ограничения:

| # | Ограничение |
|---|---|
| (1) | Энергия: `t_k ≤ T_max,m · (1 − 0.2)`, для 201 еще `L_k ≤ 210 км · 0.8` (линейная модель, QA) |
| (2) | Из любой точки маршрута достижима назначенная площадка по оставшемуся проверенному маршруту |
| (3) | Вне запретных зон с учетом высот и времени действия; над препятствиями — с запасом по высоте |
| (4) | Сближение двух бортов в воздухе не ближе R_разв по горизонтали (50 м для коптеров, 150 м если в паре самолет), если по вертикали ближе 30 м |
| (5) | Высота AGL ≤ min(коридор, потолок модели, облачность − 50 м); AMSL ≤ 4000 м; высота съемки не ниже минимальной для типа |
| (6) | Ветер на рабочей высоте ≤ допустимого по ТТХ; воздушная скорость самолета в диапазоне 64–130 км/ч |
| (7) | Съемка при высоте Солнца ≥ 10° (длинные тени, QA) |

Задача NP-трудная: это покрытие с разбиением плюс маршрутизация с ограничением по энергии плюс расписание с ресурсами. Мы используем декомпозицию: точные подзадачи там, где это возможно, и эвристики с поиском по параметрам верхнего уровня.

**Режим без плана полета** (`airspace_mode=no_flight_plan`, ФП ИВП) ужесточает (5): потолок 150 м над землей, съемка не выше 120 м, один слой перелета 145 м. Добавляется ограничение удаления от площадки R (прямая видимость): галсы обрезаются кругами радиуса R, вылет и смена площадки проверяют удаление всех точек. Высота перелета кусочно-постоянная: участки дробятся, пока высота над минимумом рельефа участка не уложится под потолок, при этом она остается не ниже max(рельеф + 30 м, верх препятствия + 30 м). Непокрытое закрывается жадным покрытием множества кругами видимости (рекомендация площадок). См. [AIRSPACE_MODES.md](AIRSPACE_MODES.md).

## 0. Модель энергии

Бюджет вылета — 80% заряда. По умолчанию расход считается пропорциональным времени полета. В режиме `calibrated` расход считается по режиму полета: Σ f(режим)·dt / T_max, где f — безразмерная кривая мощности, обученная на открытой телеметрии. Подробности — в [ENERGY_MODEL.md](ENERGY_MODEL.md).

## 1. Геометрия съемки (`sensors.py`)

Для кадровой камеры (матрица w×h мм, N_w пикселей, фокусное f):

- размер пикселя p = w/N_w;
- высота съемки H = GSD·f/p;
- полоса поперек маршрута W = w·H/f; длина кадра вдоль маршрута L = h·H/f;
- шаг галсов d = W_eff·(1 − поперечное перекрытие);
- базис b = L_eff·(1 − продольное перекрытие).

Скорость съемки ограничена:
- ТТХ с учетом ветра;
- частотой затвора: v ≤ b/t_min;
- смазом: v ≤ 0.5·GSD/t_exp.

Если высота H ниже минимальной безопасной, выдается рекомендация по GSD. Если выше коридора, облачности или ТТХ, высота ограничивается, а GSD получается лучше заданного.

Лидар: W = 2H·tg(FOV/2), скорость подбирается по плотности точек. Геофизика: шаг и высота задаются методикой. Для этих типов съемки сенсоры типовые — в линейке задачи их нет, это допущение.

**Ветер.** Замер на 10 м пересчитывается на высоту полета по степенному профилю w(h) = w₁₀·(h/10)^0.143. В режиме QA путевая скорость постоянна; следующие ограничения треугольника скоростей применяются в режиме `physical`. Галсы летаются в обе стороны, поэтому для направления галса с составляющими ветра w∥ и w⊥:

- коптер: v ≤ √(V_max² − w⊥²) − |w∥|;
- самолет: v ∈ [|w∥| + √(V_min² − w⊥²), √(V_max² − w⊥²) − |w∥|];
- у самолета худший угол сноса для двух направлений α = atan2(|w⊥|, V_ground − |w∥|). Используются ветер на рабочей высоте и скорость конкретного направления. Эффективная полоса W_eff = W·cosα − L·sinα. Уменьшенный базис повторно проверяется по минимальному интервалу камеры; недопустимый курс не подменяется номинальной скоростью.

## 2. Курс галсов и декомпозиция (`coverage.py`)

Эффективная область R* = (R ∩ A) \ [(Z ⊕ буфер_m) ∪ (⋃{O_j : h_j + clearance_m > H_m} ⊕ 30 м)]. Вертикальный запас clearance_m — 100 м у 201 и 30 м у коптеров. Буфер зон зависит от типа: у самолета 200 м, у коптера 40 м.

Сначала невыпуклые компоненты режутся на почти выпуклые части. Пока выпуклость (площадь / площадь выпуклой оболочки) < 0.75, часть рассекается поперек длинной оси минимального описанного прямоугольника в одном из 5 положений — выбирается разрез, максимизирующий выпуклость худшей половины. Так коридор трубопровода с поворотами получает свой курс на каждом прямом участке. На демо-трубопроводе это дало −39% времени и −40% налета.

Для каждой части перебирается курс θ: шаг 2° плюс направления ребер выпуклой оболочки (минимум ширины достигается на них). Минимизируется оценка времени

  J(θ) = Σ_m [ S / (d_m(θ)·v_m(θ)) + (ширина⊥(θ)/d_m(θ))·t_разв,m(θ) ].

Первое слагаемое учитывает ветер через d(θ) и v(θ), второе — число разворотов. В результате галсы идут вдоль длинной стороны и так, чтобы ветер не «съедал» скорость и перекрытие.

Компонента в СК галсов режется сеткой ячеек G×G, где G ≈ √(S/(12·N_бортов)), от 300 до 1500 м. Галсы строятся сканлайном по правилу чет-нечет по всем кольцам, поэтому корректно обрабатываются MultiPolygon и отверстия. Линии выровнены по всей компоненте, соседние ячейки одного типа сшиваются без зазоров. Галсы удлиняются на L/2 за край (полное продольное перекрытие), но не заходят в запретные зоны.

Нарезка идет колонками ширины C, обход змейкой. Внутри колонки отрезки, разделенные отверстием, группируются в «полосы»: это упрощенная клеточная декомпозиция boustrophedon. Так борт не перескакивает через препятствие на каждом ряду.

## 3. Вылеты (`sortie.py`)

Галсы в порядке обхода упаковываются в вылеты жадно. Очередной галс добавляется, если после него хватает энергии на возврат к площадке:

  t_фикс(эшелон) + t(площадка→первый галс) + Σ (L_i/v + t_перех) + t(конец→площадка) ≤ k·T_max·0.8,  k = 0.97 (коптер) / 0.99 (самолет).

Оценка учитывает то, что точная траектория сделает на самом деле:
- **обход запретных зон на перелетах** — длина перелета площадка ↔ точка умножается на коэффициент обхода (длина маршрута по графу видимости / прямая), кэш по клеткам 250 м;
- **переходы между галсами, закрытые на рабочей высоте** (препятствие, зона) — подъем на эшелон, перелет в обход и снижение, как в траектории;
- **добор кромок** у зон (полосы, которые самолет не снимает из-за разворотов) упорядочивается цепочкой «ближайший сосед», чтобы вылет собирал соседние полосы, а не прыгал между зонами.

Раньше оценка считала всё по прямой. У зон точная траектория не укладывалась в АКБ, и ремонт отрезал хвосты в отдельные короткие вылеты. На демо «Токсово» такие вылеты давали до 26% налета при 0.5% съемки. Теперь оценка совпадает с точным построением с точностью 1–3%. Налет при минимуме налета снизился на 16% при 8 и 10 бортах, время работ у одного Gemini — на 18% (физическая модель ветра, сравнение с прежней версией в [BENCHMARK.md](BENCHMARK.md)).

Галс, который целиком не помещается, делится бинарным поиском доли, остаток открывает следующий вылет. Площадка вылета выбирается как минимизирующая перелеты туда и обратно среди допустимых по энергии.

**Ветер** (`wind_model`). По умолчанию — методика QA-сессии: автопилот держит путевую скорость, ветер — порог выполнимости по ТТХ на рабочей высоте (профиль Хеллмана) и параметр выбора курса галсов (снос кадра самолета). На скорость и расход АКБ ветер не влияет. Режим `physical` считает путевую скорость по треугольнику скоростей для каждого направления: встречный ветер замедляет съемку и перелеты. Это консервативная оценка.

Если даже 60 м галса недостижимы с резервом 20%, участок **невыполним**. Тогда выдается рекомендация: точка новой площадки на 0.6·радиуса от участка вне запретных зон или другой тип БВС.

4D-траектория вылета:

- **коптер:** вертикальный взлет → свой эшелон → перелет в обход зон. Высота кусочно-постоянная: максимум рельефа на участке плюс эшелон. Далее снижение на H → галсы с огибанием рельефа (профиль упрощается Дугласом–Пекером с допуском 3 м) → набор → возврат → посадка;
- **самолет:** катапульта → спиральный набор над площадкой → … → спираль снижения над началом галса. Развороты — вынос на R и дуга радиуса max(R, d/2), где R = V²/(g·tg30°) ≈ 85 м. Посадка — спираль до 100 м и парашют.

Если переход между галсами блокирован препятствием на рабочей высоте, борт «перепрыгивает» через него на своем эшелоне.

**Ремонт по энергии.** Если точная траектория превышает бюджет АКБ, двоичным поиском находится наибольшее число галсов, при котором вылет укладывается. Для этого нужно log₂ n перестроек, обычно одна. Отрезанный хвост переносится в начало следующего вылета того же типа, если тот начинается рядом (до 2.5 км, а без плана полета — в пределах прямой видимости его площадки). Отдельный вылет ради одного галса создается, только если переносить некуда. Профили огибания рельефа кэшируются, поэтому перестройки дешевые.

## 4. Распределение площади между типами (`optimizer.py`)

Ячейки сортируются по удаленности от площадок. Типы сортируются по радиусу действия, дальние ячейки получают дальнобойные типы. Кромки у запретных зон, которые самолет не может снять из-за разворотов, передаются коптерам как добор. Параметры поиска:

- доли площади по типам (сетка на симплексе с шагом 0.1–0.25 и локальное уточнение);
- ширина колонок нарезки C ∈ {2G, 4G, 8G, ∞} для каждого типа.

Каждый вариант оценивается полностью: галсы → вылеты → расписание → критерий. Одна оценка занимает ~50–100 мс, поэтому поиск укладывается в секунды или минуты.

По умолчанию сетка дополняется **байесовской оптимизацией** (TPE, Optuna; `optimizer="bayes"`):
- пространство поиска шире сетки: непрерывные доли площади, непрерывная ширина колонок каждого типа (или «на всю ширину»), масштаб сетки ячеек 0.6–1.6;
- TPE строит вероятностные модели «удачных» и «неудачных» проб и выбирает следующую пробу по ожидаемому улучшению;
- теплый старт — лучший вариант сетки;
- бюджет — 20/60/150 проб в режимах быстро/нормально/тщательно.

На 28 задачах (демо и случайные сценарии, два критерия) по фактическому результату после полного построения байесовская оптимизация лучше сетки в 9 задачах (максимум −19.4%), равна в 19, хуже — ни в одной; среднее изменение критерия по всем 28 задачам −2.1%. Выигрыш — в критерии «время»; по налету варианты сетки уже оптимальны. Подробности — в [BENCHMARK_BO.md](BENCHMARK_BO.md).

Затем **финальный отбор**: лучшие по оценке варианты каждого метода (3 от сетки и 3 от байесовской оптимизации) проходят полное построение — точные траектории, ремонт по энергии, 4D-разведение. Выбирается лучший по фактическому критерию. Это страхует от расхождений оценки на границах светового дня.

Журнал поиска и финальные кандидаты сохраняются в плане (`search_log`, `final_candidates`) — видно, почему выбран именно этот вариант.

## 4а. Площадки, зоны и большие сцены

- **Площадки не заданы** (задание организаторов «Границы полетов.kml»). Площадки расставляются жадным покрытием множества: круги досягаемости самого «короткого» типа в парке (для Gemini ≈ 5 км) покрывают точки области, положение уточняется k-медианами (минимум среднего перелета), площадка выносится из запретных зон. На задании 245 км² — 28 площадок.
- **Зоны с высотами.** Нижняя граница зоны в AMSL (эшелоны FL, «от 800 м AMSL») пересчитывается в высоту над землей по максимуму рельефа под зоной в районе работ. Зона выше коридора не влияет, зона выше рабочих высот ограничивает эшелоны, остальные вырезаются из съемки. Формат — [ZONE_FORMAT.md](ZONE_FORMAT.md).
- **Масштаб маршрутизации.** Граф видимости строится лениво (большинство перелетов прямые). До 700 узлов — полный граф, больше — разреженный: k = 28 ближайших видимых соседей, все ребра проверены на пересечение с зонами. Длины перелетов «площадка → точка» для упаковки берутся из дерева кратчайших путей от каждой площадки (scipy Dijkstra) через ближайшие видимые узлы. Препятствия у съемочного графа — только в 3 км от области. На задании организаторов (1837 препятствий, 17 зон, 570 участков) подготовка и поиск — минуты, а не часы.
- **ЦМР для большой территории.** Если район не помещается в 100 тайлов z12, берется z11 (≈ 40 м/пикс), а не отключается рельеф.

## 5. Расписание (`dispatch.py`)

Используется list scheduling: следующий вылет отдается борту с самым ранним возможным стартом. Для борта рассматриваются первые 24 вылета очереди, при равном старте — с его текущей площадки. Без этого на задании с десятками площадок борт переезжал почти после каждого вылета: срок работ задания организаторов сократился на 21%. Старт ограничен:
- временем, когда борт свободен после обслуживания (замена АКБ, выгрузка, для 201 — укладка парашюта);
- наличием заряженной АКБ (B комплектов, зарядка по ТТХ);
- переездом расчета между площадками;
- светлым окном;
- окнами действия временных запретных зон, которые задевает вылет.

Время выполнения считается с развертывания расчета до посадки последнего борта плюс выгрузка данных.

## 5а. Подбор парка к сроку (`advisor.py`)

Ответ организаторов: пользователь задает ограничения (число бортов или срок) и получает подсказку. Маржинальный анализ: для каждого n = 1…N кандидаты — жадный шаг от лучшего парка n−1 (каждый тип) и пропорциональный доступному парку состав. Каждый оценивается быстрой оценкой планировщика, которая совпадает с точной траекторией в пределах нескольких процентов. Время работ — ступенчатая функция: световой день и ночь. Поэтому берется огибающая: лишние борта можно не поднимать, и кривая монотонна.

Результат:
- минимальный парк, укладывающийся в срок;
- «колено» — наименьший парк в пределах 5% от лучшего времени;
- если доступного парка мало — продолжение сверх него (до 12 бортов каждого типа) с ответом «потребуется N бортов».

## 6. Разведение бортов в расчетной модели

1. **Эшелоны.** Каждому борту выделен свой эшелон перелета выше всех съемочных высот: база = max H + 30 м, шаг 35 м. Коптерам достаются нижние эшелоны.
   - Зоны с ограничением по высоте опускают потолок эшелонов, а не блокируют съемку под собой.
   - Потолок ограничен и высотой, на которой ветер (растущий с высотой) достигает предела ТТХ. Если ветер превышает предел уже на нижнем эшелоне, тип БВС исключается с объяснением.
   - В низинах участок перелета дробится, чтобы высота над землей не выходила за потолок.
   - Временные зоны: окна запрета для вылета определяются по его фактической траектории (галсы, переходы, перелеты), и вылет целиком ставится вне окна.
2. **Пространство.** Съемочные участки разных вылетов не пересекаются.
3. **Время.** Каждая новая траектория дискретизируется с шагом 1 с и проверяется против принятых на совпадения, когда оба борта в воздухе (выше 1 м над землей — строже независимой проверки с ее 3 м): горизонталь < R_разв + путь за шаг и вертикаль < 33 м. Конфликт снимается задержкой старта на земле. Если подходящего светового/временного окна или решения в лимите поиска нет, возвращается отказ.

Сложность проверки — O(Σ_k пересечений по времени), она векторизована в numpy.

## 7. Независимая проверка (`validate.py`)

Проверка работает только с выходными точками (WGS-84 плюс время) и исходным сценарием, проекция у нее своя. Проверяются ограничения (1)–(7). Для зон учитываются высотный диапазон AGL/AMSL и окно действия. Результат — список проверок с деталями, он выводится в интерфейсе и в `summary.json`.

Пересечения зон и препятствий проверяются по отрезкам, ограниченным по времени и высоте. Для сближений ищется минимум квадрата расстояния двух линейных траекторий между событиями; проверяются и промежутки между целыми секундами. AGL и длина маршрута пересчитываются по выходной геометрии. Дополнительно проверяются уникальность вылетов, доступный парк, отсутствие перекрытия вылетов одного борта, площадки, обслуживание, АКБ, переезды и срок. Провал любой проверки запрещает статус `ok`. Рельеф между точками остается дискретной моделью. Ограничения и актуальные измерения приведены в [аудите](AUDIT_2026-09-25.md); исторические бенчмарки ниже не являются повторной проверкой текущей версии.

## Сложность

Обозначения: n — число галсов, k — число вылетов, m — число вершин запретных зон.

| Шаг | Сложность |
|---|---|
| Курс галсов | O(90·|hull|) |
| Сканлайн | O(n·|ребра|) |
| Упаковка | O(n·log(1/ε)) |
| Граф видимости | O(m²) один раз, запросы O(m log m) |
| Расписание | O(k·N_бортов) |
| Разведение | O(k·K·T/Δt), где K — число перекрывающихся по времени вылетов, T/Δt — длина трека в секундах |

На 100 км² и 8 бортах: ~70 вылетов, ~20–40 тыс. 4D-точек. Расчет занимает 3–5 с в режиме «быстро» и до 1–2 мин в режиме «тщательно».
